MaxHook Native 上报 · 方案 1：加密边界复用

流程报告 · 2026-08-13 · 基于 3 轮动态捕获与 60+ 项算法排除实验
一句话结论：MaxHook 的外层上报信封使用 VM 保护的私有流密码（无任何标准密码常量），无法离线复现。 但 加密边界 hook 已能在 0x180324610 完整截获 (明文 JSON, 会话密钥材料, 最终 envelope) 三元组——方案 1 让 proxy 直接复用真实加密输出，即可满足 "native 上报通道不判协议无效" 的工程目标。

1. 目标

为「无真实白端的协议模拟进服」提供 native 侧上报通道的可行工程路径： 在不理解私有加密算法的情况下，让 proxy 发送与 MaxHook 一致的合法 envelope，被 security.mcbjd.net 接受。

约束说明
不可离线复现算法外层信封是私有流密码，无标准常量、无 AES-NI、无 CNG 调用
必须合法服务端会校验 tag（AEAD 认证），伪造数据返回非 200 或触发黑屋
低风险不能注入 / 不能常驻调试器（此前 Frida attach 已触发过一次黑屋）

2. 已确认的协议事实（证据链）

2.1 端点与调用顺序

POST https://security.mcbjd.net/api/v3/session/bootstrap/redeem    （会话引导, 1 次）
POST https://security.mcbjd.net/api/v3/session/exchange            （密钥交换, 1 次）
POST https://security.mcbjd.net/api/v3/report                      （周期上报, 每 ~30s）

IP：111.124.198.121:443 · HTTP/1.1 Keep-Alive · Content-Type: application/json · 22/22 组双向样本验证

2.2 外层信封（Envelope）

客户端请求（22/22 一致字段顺序）

{"ciphertext":"<hex>",
 "kid":"<32 hex>",
 "nonce":"<24 hex = 12B>",
 "sv":3,
 "tag":"<32 hex = 16B>"}

服务器响应（字段顺序不同！）

{"sv":3,
 "kid":"<32 hex>",
 "nonce":"<24 hex>",
 "ciphertext":"<hex>",
 "tag":"<32 hex>"}

密文长度 = 明文长度（流式、无填充）· KID 在 session/exchange 与 report 之间切换（两套密钥标识）· 响应 KID 与请求配对

2.3 加密前明文（外层信封的 plaintext，完整截获）

{"device_id":"6B4F2E745394C479",
 "h2_cantor":"v2:<MD5 16B>:<SHA-256 32B>",      // Cantor 双哈希
 "nonce":"b4352b9afd7f933f22f6564193ecd28c",        // 内层 nonce (16B)
 "report_packet":"<104B hex>",                     // 内层加密报告
 "seq":90,                                           // 上报序号递增
 "session_id":"58638509E9D05B6C12209C942D10D7D6",   // 32 hex
 "sv":3,
 "timestamp":1786609159999}

注意：信封内还有一个内层 report_packet（104B hex），说明存在双层加密：外层保护整个 JSON，内层保护设备报告。

2.4 加密边界参数布局（hook 捕获验证 7/7）

0x1803cf7c4  mov [rsp+0x20], rsi        ; 第5参 = plaintext JSON (std::string)
0x1803cf7c9  lea rcx, [rbp+0x290]        ; output envelope (4 个连续 std::string)
0x1803cf7d0  lea rdx, [rbp+0x0E0]        ; 32-char 输入 = KID
0x1803cf7d7  lea r8,  [rbp+0x1A0]        ; 64-char 输入 = 会话密钥材料 (hex)
0x1803cf7de  mov r9, rdi                 ; context (JSON 序列化字段表 @ rbp+0x38)
0x1803cf7e1  call 0x180324610            ; ★ 加密边界 → jmp VM 0x181523001
对象内容验证
output +0x00kid_hex (32)7/7 size 正确
output +0x20nonce_hex (24)7/7 每次不同
output +0x40ciphertext_hex (可变)7/7 = 明文长度×2
output +0x60tag_hex (32)7/7 size 正确
context 内协议标记hpac.v3.session.report.req跨调用恒定

3. 为什么不能离线复现（算法排除实验）

验证项尝试规模结果
AES-GCM / AES-CCM / ChaCha20-Poly13057 样本 × 30+ key 派生 × 12+ AAD0 命中
AES-CTR keystream 匹配key 变体 × nonce 布局 × counter 0-256 × BE/LE0 命中
tag = HMAC-SHA256/SHA1/MD5 截断11 种拼接材料 × 6 MAC 变体 × 5 key0 命中
input64 派生hex/ASCII/哈希/字节序/XOR 掩码/组合 60+非直接 key
静态密码常量扫描S-box / T-tables / ChaCha / SHA / MD5 / AES-NI.bugland 全零命中
判定：加密函数 0x180324610 → VM 0x181523001 是自实现/混淆的私有流密码， 常量表在 VM 内即时解密、用完即弃——与检测名单同一保护机制。离线复现需解 Themida VM（另一个 agent 进行中）。

4. 方案 1：加密边界复用（推荐工程路径）

1
真实客户端进程内挂载边界 hook

运行 capture_maxhook_encrypt_boundary.py（Frida，仅 hook MaxHook.dll+0x324610 一个点）。黑屋状态不影响——协议仍在运行。

uv run --with frida -- python capture_maxhook_encrypt_boundary.py \
  --process javaw.exe --output .\native_capture \
  --ack-sensitive-local-capture --duration 0   # 手动停止
2
边界上截获完整三元组
阶段数据
onEnter明文 JSON · KID (32 hex) · 会话密钥材料 (64 hex) · context
onLeave输出 envelope：kid / nonce / ciphertext / tag
3
Envelope 服务（proxy 集成点）

hook 进程内维护一个本地通道（命名管道 / localhost WebSocket），将每个周期捕获的 (plaintext → envelope) 映射推送出去。Proxy 收到真实 envelope 后原样发送到 security.mcbjd.net/api/v3/report——加密正确性由真实 MaxHook 保证。

4
会话联动

KID 在 bootstrap/exchange 后切换——Envelope 服务需要保持与游戏会话同生命周期： 游戏进服后启动、会话结束时停止；proxy 侧按 KID 匹配事务（请求/响应 KID 必须配对）。

5
局限与降级

本方案依赖真实客户端进程存在（不能完全脱离 DLL）；若目标账号长期黑屋，建议用纯净小号承载 hook， 主号流量由 proxy 转发——会话/上报身份均来自 hook 侧实例。

5. 与替代方案的取舍

方案完全离线工程量风险状态
① 加密边界复用（本方案）否（需真实 DLL）低（hook 已就绪）低可立即落地
② Frida Stalker 跟踪 VM部分中中尝试中
③ VM 硬破（另一 agent）是高—进行中
