## 三、密码算法完整规格（可复现）

### 3.1 加密流程

```
encrypt(0x180324610):
  envelope = {sv:3, kid, nonce, ciphertext, tag}
  1. key   = hex_decode(input64)          # 32B
  2. nonce = internal_CSPRNG()             # 12B (VM 内部定制 PRNG)
  3. state = key_schedule_expand(key, nonce)   # → 状态缓冲（唯一剩余 hook）
  4. keystream = generator(state)          # 64B 块流
  5. ciphertext = plaintext XOR keystream
  6. tag = MAC(key, nonce, ciphertext, aad)    # 16B
```

### 3.2 ARX 轮函数（已解码）

```python
def arx_round(s1, s2, const3, constA):
    s1 ^= ((const3 ^ s1) - s2) & 0xFFFFFFFF
    s1 ^= (constA + s1 + s2) & 0xFFFFFFFF
    return s1, s2
# const3 = word[VIP+3], constA = word[VIP+0xa]（16-bit 字节码字）
```

### 3.3 VM dispatch（静态证明，milestone 17）

```python
def vm_dispatch(word, key):
    index_full = (word - (key & 0xFFFF) + 0x5214A88C) & 0xFFFFFFFF
    index = index_full & 0xFFFF
    key_after = (key - index_full) & 0xFFFFFFFF   # DATA-DRIVEN: key=word[VIP+key_off]
    return index, key_after
# handler 表 0x180c64ebd（1612 条目）
```

### 3.4 执行链（第 154-160 轮确立）

```
VM INIT (373 步, key 无关)
  → 0x180322bd3 (indirect call)
  → 明文 key-schedule wrapper 簇 (0x180322a20..0x180322ed0)
  → helper 表 0x1807bdc70 (16 函数) 表驱动 ARX
  → state 缓冲
  → generator 0x18041a8a0
  → FN 表 0x1807d7c70 (VM stubs, jmp 进 .bugland)
  → store32 0x18041a860 → keystream word
```

## 四、第 214 轮新增确认（本轮）

### 4.1 明文 key-schedule wrapper 簇完整反汇编

`0x180322a20..0x180322ed0` 已完整反汇编，确认是 **表驱动的字节码解释器**（非简单 ARX 链）：

- **薄 wrapper**（`0x180322a20`/`0x180322aa0`/`0x180322ae0`）：各自读 std::string 字段
  （`[rcx]`=data / `[rcx+8]`=size），ARX 解码 helper 索引，`call [0x1807bdc70 + idx*8]`
- **主 dispatcher** `0x180322b60`（body `0x180322b80`）：读全局索引 `0x1807c7450`
  （= 静态小整数表：1/2/3/4/8/6...），索引数据表1 `0x180658b48` 得字节码字，经
  rol/ror/not/bswap/neg + XOR 常量（`0xacec895a`/`0x5a89ecac`/`0x44e924`/`0xffbb16db`/
  `0x7fcb1992`/`0xa4dbc339` 等）解码出 helper 索引，`call [0x1807bdc70 + rax*8]`
- **字符串比较函数** `0x180322d10`：逐字节循环（`movzx edx,[rdi]`/`inc rdi`/`cmp rdi,rsi`），
  每字节经 ARX 解码调 helper——标准 std::string 比较/校验语义

### 4.3 keystream generator 定位（本轮复核）

- generator dispatcher `0x18041a8a0`（明文）
- FN 表 `0x1807d7c70`：16 条目（VM stubs + store32 `0x18041a860` + generator 自身）

### 4.4 关键证据：key-schedule wrapper 仅被 VM 间接调用

`.text` 全文扫描 `0x180322a20`/`0x180322b60`/`0x180322d10` 的 `call imm`/`lea rip` 交叉引用：
**0 条**。证实这些函数仅由 VM（.bugland）经间接 call 驱动——这解释了为何 rcx/rsi 在
walker 逐 handler 执行时丢失（walker 无法保留 VM 建立的输入 struct 指针）。

## 四·五、第 215 轮新增确认（本轮）

### 4.5 差分密码分析：排除简单构造

`differential_cryptanalysis.py` 用 writer_sync 的 3 组（同 key `347230E6...`、3 个不同 nonce）
做差分分析：

- **H1 可分离性**（ks0 = f(key) XOR g(nonce)）：keystream word0 差分
  `0xf27d3ce7/0x5dc00a3e/0xafbd36d9` 与任何 nonce 单字差分均不匹配 → 非简单可分。
- **H2/H3 简单状态初始化**（ks0 = k0^n0、k0+n0、k0^n0^n1^n2、k7^n0 等 8 种）：**全部不匹配**。
- **H4 块计数器**（blk0^blk1 = 计数器）：3 组块间 XOR 无规律（`0xdfa5ab85`/`0xecdc2ce4`/
  `0x42e46cce`）→ 非简单计数器。

**结论**：密码是真 ARX 流密码，nonce 全扩散（非弱加性），无简单密钥流捷径——key-schedule
必须是完整的表驱动 VM 程序，无法用简单公式拟合（与 `final_arx_fit.py` 第 179 轮结论一致）。

### 4.6 单 handler 执行：隔离 heap key 缓冲依赖

`execute_single_handler.py` 以真实 vm_enter_context 执行 handler body `0x180c0304d`
（index 0x5d0）：

- 执行 157 指令后 crash 于 `0x180c03345: shr word ptr [rax], cl`（读未映射 heap 指针）。
- 上下文槽 +0x0/+0xa/+0x5d/+0xe5 被修改（key/state 槽），证明 handler 是真实 key-schedule ARX。
- **根因**：handler 需要 heap key 缓冲，但 vm_enter_context（encrypt 入口）的指针槽
  +0x45=`0x1807bf900`（模块 .data）、+0x61=`0x86dfff610`（栈）、+0xbd=`0x1807bdc70`
  （helper 表）——**key 缓冲在 key-schedule 运行中才分配**（key hex 解码后拷贝到 heap），
  encrypt 入口尚未分配。

**结论**：keystream 复现需要执行 key-schedule 的**前缀**（key hex 解码 → heap 分配 →
state 初始化），而 vm_enter_context 捕获的是该前缀**之前**的状态。这精确界定了剩余缺口：
不是"依赖真机运行时状态"，而是离线 dump（pid 41264 空闲态）未包含 key-schedule 运行中
分配的 heap key 缓冲（pid 42948 的 `0x13a4e192070`）。

## 四·六、第 216 轮：SHA-256 组件决定性发现

`encrypt_vm_clean_complete.json`（4.16M 指令离线执行产物）的 heap write 追踪发现**协议使用 SHA-256**：

- SHA-256 IV 常量（`0x6a09e667`/`0xbb67ae85`/`0x3c6ef372`/`0xa54ff53a`/`0x510e527f`/
  `0x9b05688c`/`0x1f83d9ab`/`0x5be0cd19`）由 `0x18042b970` 写入 112B SHA-256 上下文
  （inst 4149897-4150170），**逐字匹配 FIPS 180-4**。
- 完整 heap 分配布局：key(32B) + AAD 字符串 `v3|hpac.v3.session.report.req`(27B) +
  kid(16B) + nonce(12B) + SHA-256 上下文(112B)。
- key 消费者定位：解码 key 于 inst 1403261 被 `0x1805d0c36`(memcpy) 4×8B 读入 key-schedule。
- **修正既有结论**：keystream 密码是定制 ARX，但 **tag MAC 使用 SHA-256**（非纯 ARX）。
- 已排除 15 种简单 HMAC-SHA256/SHA-256 tag 组合（`test_tag_sha256.py`），MAC 精确消息布局
  （可能含 key 派生 MAC key）待定。

详见 `MaxHook_协议栈_SHA256组件发现_第216轮_2026-08-14.md`。

## 四·七、第 217 轮：MAC 派生密钥统一假设

- **完整 SHA-256 确认**：全部 64 个 SHA-256 轮常量 K（`0x428a2f98`...`0xc67178f2`）在 DLL
  中逐字存在（LE，64/64），证实是标准 SHA-256（非截断/非变体）。
- **统一假设**：~90 种 MAC 构造（`test_mac_systematic.py`：HMAC-SHA256 × 8 种 key 派生 × 6 种
  消息顺序 + SHA-256 长度编码 + nonce 作 key + HKDF-like）全部 0/10 匹配 → **tag MAC 密钥是
  key-schedule 派生的，非原始会话密钥**。故 keystream 与 tag 收敛于同一个
  `key_schedule_expand(key, nonce)`。
- **nonce 指针定位**：`0x20000100080`（12B nonce）指针存储于 VM 上下文槽 +0x61（`0x18098c8e5`）。
- **nonce 非 SHA-256 派生**（`test_nonce_sha256.py`）：内部 CSPRNG，非 key+counter 哈希。

详见 `MaxHook_协议栈_MAC派生密钥统一假设_第217轮_2026-08-14.md`。
