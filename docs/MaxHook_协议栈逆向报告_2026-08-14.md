# MaxHook 协议栈逆向报告：已完成闭合与剩余边界

日期：2026-08-14
范围：纯离线（仅原版 `target/MaxHook.dll`、离线解压产物、本地捕获，无真机 hook/attach/Stalker）

## 0. 结论速览

本报告对 MaxHook 报告加密信封 `{sv,kid,nonce,ciphertext,tag}` 的协议栈做了**逐层剥离**。已**完整闭合**的层：

1. 原版 `.boot` → `.bugland` 离线解压（99.9608% 匹配运行态）；
2. Themida 重定位/fixup 层（稀疏补丁后 `.bugland` 与运行态 **100% 匹配**）；
3. writer 调用语义（`0x18041a860` 通过 `popfq;ret` trampoline 调用，非普通 call）；
4. writer trampoline 的完整虚拟栈 ABI（S10→RDX 等）。

**剩余未闭合**的层（运行态 key-schedule 产物，离线不可重建）：

- context+0x61 / context+0xc5 指向的运行时密钥流状态缓冲区；
- 真正的 `store32` 命中的密钥流轮函数与 128 位 MAC。

## 1. 协议信封结构

```text
{ sv:3, kid, nonce, ciphertext, tag }
```

- 输入 `input64` 直接 hex 解码为 32 字节会话密钥材料；
- 输出为 4 个连续 MSVC `std::string`（+0x00 kid, +0x20 nonce, +0x40 ciphertext, +0x60 tag）；
- nonce 12 B，tag 16 B，ciphertext 长度等于 plaintext。

## 2. 已闭合层 A：`.boot` 解压

- 原版 `MaxHook.dll` `.boot`（RVA 0x1f00000）与运行态逐字节一致；
- 离线 Unicorn 从入口 `0x181f00058` 解压到 `0x181f00246 jmp rax`，得到 `0x180c0eb27`；
- 解压产物 `boot_unpacked.bin` 覆盖 `0x180980000..0x181efc000`，与运行态 `.bugland` **99.9608%** 一致（22,528,000 字节中仅 8,841 字节不同）。

## 3. 已闭合层 B：Themida 重定位/fixup

- 8,841 字节差异被精确定位为 Themida fixup：
  - 64 位基址重定位（+0x180000000）；
  - 导入解析（0x7ffc…）；
  - 运行时指针初始化（0 槽 → 绝对 VA）。
- 单个关键槽 `0x18098f97c`：解压产物 `0x000000000df09e59` → 正确值 `0x00000001809a62b3`（三个独立来源：oracle、runtime_bugland.bin、runtime_bugland2.bin 全部一致）。
- 该地址是 `.bugland` 内 handler 桥 `0x1809a62b3: jmp 0x180d639d9`。
- 读取链：`0x180a26421 add r14,rbp` → `0x180a26432 mov r14,[r14]` → `0x180a2643f mov r14,[r14]`。
- 未修复后果：`r14=0xdf09e59` 写 context+0x106、压栈，`0x180c1b2f3 ret` 弹出当返回地址 → fetch 崩溃。
- 修复方式（same-instance）：把 oracle 与解压产物差异做成稀疏补丁（2,880 runs / 8,841 字节），在解压后真实入口前就地 `mem_write`，使 `.bugland` 与 oracle **100% 匹配**。

## 4. 已闭合层 C：writer 调用语义（纠正）

- **不是普通 `call`**。`0x18041a860 store_le32` 是通过伪造完整寄存器帧后 `0x180c27931 jmp 0x180c2775c`（`popfq; ret`）进入的。
- `capture_maxhook_writer_calls.js` 记录的 `return_address=0x181ad61e7` 是 writer 入口 `[rsp]` 的值，不是 call 后继。
- 此前子报告误写 `0x181ad61e2 call store32`、`0x181ad61de EDX producer` 均不成立。
- 每个 writer 命中都是 `caller_block=0x180c2775c` + `return_address=0x181ad61e7`。

## 5. 已闭合层 D：writer trampoline 虚拟栈 ABI

对 `keystream_slot_changes_capture_20260814` 的真实动态序列做符号执行，`symbolic_writer_trampoline.py` 恢复：

```text
0x180c278a7 -> 0x180c27786 -> 0x180c27652 -> 0x180c27bf9 -> 0x180c279b4
-> 0x180c27673 -> 0x180c27bd0  mov rdx,[rsp]   (S10)
-> 0x180c27a5b  mov rcx,[rsp]   (S11)
-> 0x180c27900 -> 0x180c2775c  popfq; ret
-> 0x18041a860  store_le32
-> 0x181ad61e7  continuation
```

入口栈布局（`[rsp+n*8]=Sn`）：

```text
S1  -> R11
S2  -> R12
S3  -> R13
S4  -> R14
S5  -> R15
S6  -> RDI
S7  -> RSI
S8  -> RBP
S9  -> RBX
S10 -> RDX = 真 32-bit keystream word
S11 -> RCX = 输出地址
S12 -> RAX
S13 -> RFLAGS
S14 -> RIP = 0x18041a860
```

证明 writer 前缀是"从 VM 虚拟栈恢复完整宿主寄存器帧并 RET 调用 native helper"的 trampoline，EDX 不是 0x181ad61e7 附近算出的。

## 6. 已闭合层 E：store32 即最终密钥流字

`writer_sync_clean_20260814_014351/analysis.json` 证明：

- 丢弃前 12 条记录后，每 16 条记录分组能精确重构一个 64 字节 `plaintext XOR ciphertext` 块；
- 3/3 调用 `all_blocks_equal_keystream=true`；
- store32 的 EDX 就是最终 32-bit little-endian 密钥流字。

## 7. 已闭合层 F：离线重放推进（same-instance pipeline）

- `scripts/same_instance_pipeline.py` 在**单个 Unicorn 实例**完成 `.boot` 解压 → 就地 fixup → 真实入口 → 直接调用 `0x180324610`，全程不 dump/reload。
- 修复前：Phase 3 15,799 条指令后读 `0x290f51` 崩溃。
- 修复后：Phase 3 24,011 条指令，推进到 `0x180a831db` 读 `0x7ffcb75a6fe4`。
- 追加精确的每消费者表修复（`0x180a831db`→0x180835f10、`0x180bf1eb2`→0x1808374e0）后，重放**不再崩溃**，稳定跑到 4,162,212 条指令并干净退出（无未映射访问）。
- 但 `store32` 命中数 = 0，说明该入口上下文执行的是 VM wrapper 初始化/setup 段，尚未进入真正生成 64 字节块的密钥流循环。

## 8. 剩余未闭合边界（离线不可达）

修复后所有"未映射内存"类故障都被消除；剩余卡点都是**运行时 key-schedule 状态**：

1. Phase 2 `0x180a353e7` 读 `0x1ab783620d0` —— 真实进程 native 堆指针，磁盘不含。
2. context+0xc5 —— 密钥流状态源指针（里程碑 28），真机块边界一致为 `0x11a6cfee30`，其 pointee 是运行时 key-schedule 产物。
3. 真正的 `store32` 密钥流轮函数与 128-bit MAC/tag 路径未执行到。

这三个都是真机运行时状态，离线磁盘镜像/dump 均不含，纯离线重放无法重建。`context+0x61/0xc5` 的真实值来自块边界捕获，指向的缓冲区内容无法离线生成。
