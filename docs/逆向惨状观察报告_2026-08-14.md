## 一、事故现场概览

该目录的官方身份是 Java 项目 `S1mple-1.0-SNAPSHOT.jar` 的 Maven 构建产物目录（一个 Minecraft 代理）。然而考古学证据表明：某位勇士试图逆向其中的原生库 `MaxHook.dll`（一个用 Themida 壳 + 自研 VM 保护的反作弊上报模块），并把整个 `target/` 变成了战争现场。

现场共计：

| 类别 | 数量 |
|---|---:|
| 顶层文件 | 376 个 |
| Python/JS 脚本 | 约 200 个（交接文档自称 "128 个 py/js 工具"，说明**自己也数不清了**） |
| 里程碑文档 | 24 篇（编号 02–27，其中 21/22/23 **内嵌在 20 号里面**） |
| 交接/进度文档 | 4 篇（给"并行工作的 VM 硬破 agent"看） |
| AI Prompt 打包文件 | 2 份（把整场战争序列化，喂给下一个 AI 继续打） |
| 捕获数据目录 | 30+ 个（`*_capture` 家族，含 1、2、3、4 号复数版本） |
| 总占用 | **6.7 GB**（其中 5.36 GB 是一个进程的内存转储） |
| 最终密钥 | **仍未拿到** |

## 三、案情还原：三日战争全记录

### Phase 0（8/11–8/12）：一切从"看一眼 jar"开始

- 8/11 23:56：`S1mple-1.0-SNAPSHOT.jar.before-payload-inspection` —— 打包前最后一眼。此时当事人尚不知道自己即将失去三天人生。
- 8/12 全天：代理服务器（部署在 `192.168.1.30`，密码 `114514`）反复崩溃。`crash-log.txt` 显示 systemd 把它反复拉起、反复打死（`status=143`），`surefire-reports/` 里有 4 份 JVM dumpstream。
- 期间诞生 `deploy_fix.py` → `deploy_v2_fix.py` → `deploy3.py` → `deploy6.py`。**六个部署脚本，几乎同样大小，同样 114514 密码。修了六遍的东西，大概率是修不好的。**
- 8/12 18:32：`remote-log-3h.txt` 诞生，169 MB。服务器日志里出现了 `FML3` 和 `pc.bjdmc.net` —— 战争开始升温。

### Phase 1（8/13 上午）：网络考古学（里程碑 02–04）

当事人决定搞清楚代理后面的原生 DLL 在干什么。对进程做了一次 5.36 GB 的全量转储（`dump_out/41264`），然后从 10,764 个 region 文件里挖出了关键物证：

```
POST /api/v3/report HTTP/1.1
Host: security.mcbjd.net
Content-Length: 2659
```

请求体是紧凑 JSON envelope：`{"sv":3,"kid":"32hex","nonce":"24hex","ciphertext":"...","tag":"32hex"}`。里程碑 02 用对象链证据（WebIO 对象 `+0x20=2659`、header 指针、双份长度字段）**严谨地证明了这个请求体已经没了**：

```text
0x00 数量       = 2656
非零字节        = 3
可打印字节      = 0
```

**5.36 GB 的转储，换来了 3 个非零字节。** 这是本战役的第一个喜剧高潮。

里程碑 03/04 阶段又陆续发现：
- "2659 只是某一条消息的实例长度，不是协议常量"（实际覆盖 1507–16453 字节）——**一个里程碑的篇幅被浪费在证明一个数字不是常量上**；
- 双层加密：信封内还有内层 `report_packet`（104B hex）；
- 明文 schema 线索：`motherboard_count`、`mac_count`、`disk_count`、`cpu_count`——这是在采集硬件指纹；
- 三条独立的协议链：MaxHook native / NetEase EnvSDK/acSDK / HeyPixel Java。交接文档严肃注明："**不能互相借用字段或密钥**"。

### Phase 2（8/13 中午）：发现 VM，噩梦开始（里程碑 05–15）

加密边界 `0x180324610` → VM 入口 `0x181523001` → dispatcher。当事人发现自己面对的不是一个函数，而是：

- **1612 个 handler 组成的 dispatch 表**（`T=0x180c64ebd`，全部指向一个叫 `.bugland` 的段——Thêmida 官方把这块代码区命名为 "bug 大陆"，当事人默默接受了这个命名）；
- **11 个克隆 dispatcher 代码段**，分别用 `jmp rax/r11/r13/r10/rcx/r15/rdx/rbx/r14/r9/rax` 跳转（11 种寄存器轮着来，像个邪教仪式）；
- rolling key 更新规则：`key ^= key + const`（const=0x4111，从 `VIP+0xc` 读出的字节码字面量）；
- dispatch 索引公式：`index = (word[VIP+0] - key + 0x5214a88c) & 0xffff`；
- VM context 位于 `0x18098c884`：`+0x0a` rolling key、`+0x6d` VIP、`+0x85` handler 表指针。

期间还踩了两个方法论大坑：
- **翻译次数 ≠ 执行次数**（里程碑 15 自己纠正自己，把里程碑 09–12 重新分级）；
- 在 `.bugland` 内部用 `Interceptor.attach` 会触发 Themida 自校验 → **当场崩游戏**。于是只能 hook 明文 `.text` 入口，内部全部改用 Stalker `putCallout`。

### Phase 3（8/13 下午–深夜）：模拟器死亡行军（里程碑 16–23）

当事人写出了 `emulate_maxhook_encrypt_boundary.py`（Unicorn 离线模拟器）和 `phase2_*.py`（20 个版本）、`run_unpack_*.py`（7 个版本）、`trace_trap_tsc*.py`（9 个版本，针对 RDTSC 反调试的军备竞赛）、`gen_disasm*.py`（6 个版本）……

模拟器在**第 545,691 条指令**崩溃：`[0x158] CRASH`。之后是一场经典的打地鼠长跑：

| 轮次 | 崩溃点 | 根因 | 结果 |
|---|---|---|---|
| Round 1 | 545,691 | base 槽被零写，"栈 desync" | 追了半天 |
| Round 2 | 546,528 | `0x10f8e912a3b29232` 加密垃圾表 | base 选错表 |
| Round 3 | 1,296,634 | `0x1c7aa206480` 未映射 | **根因是自己模拟器漏了 `TEB+0x58`（PEB 指针）** |
| Round 4 | 1,296,634 | 同上 | PEB 内容没填充，"修复一处等价于 100 次打地鼠 patch" |
| Round 5 | 1,296,634 | 同上 | `0x1c7` 前缀 = 合法计算结果，指向 **Java 进程 1.95 TB 的 native 堆**，模拟器没映射 |

这里有个必须载入史册的转折：**排查"栈 desync"查了一整天，最终根因是自家模拟器漏了一行初始化**。当事人用 100 次运行时补丁强行推进到 1,296,634 条指令后，才用一张指令链图表证明 `pop rdx` 读到的 0 来自 `[gs:0x58]`——`TEB.ProcessEnvironmentBlock`——**模拟器只初始化了 `teb+0x30` 和 `teb+0x188`，漏了 `teb+0x58`**。0 由此传播成 base 槽零写。

紧接着 `0x1c7` vs `0x180` 前缀之谜（偏移 0x47）又烧掉几小时：从"加密表损坏"到"rolling key 偏 0x04"（subagent 算错，交叉验证打脸）到"重定位镜像"到最终真相——**`key ^= key+0x4111` 是合法字节码，`0x1c7...` 是 Java 堆地址，模拟器没映射 Java 堆**。第 4 级 dispatch 全部正确，但第 4 级之后一切都是错的环境。

里程碑 20 的文档长 428 行，里面内嵌了"里程碑 21、22、23"三个章节（Round 13–15）：
- 里程碑 21：真机抓 VM context 快照 → **59/128 字段与磁盘初始态不同**，"初始 context 就错"；
- 里程碑 22：把真机 context 灌进模拟器 → **无效**（VM 序言会重新初始化，灌进去的被覆盖）；
- 里程碑 23：静态密码学分析 → GF(2) 秩 = 7（keystream 非线性）、无 S-box、无 AES-NI、"无任何标准密码结构"、**自定义字节码编译流密码**，还原唯一路径是静态分析 1612 个 handler，"海量工程"。

**为什么里程碑 21/22/23 要内嵌在 20 里？** 唯一合理的解释：当事人写到第 20 篇时已经不想再建新文件了，或者第 21–23 号文件在某个深夜被情绪性删除。无论哪种，这都是整片遗址中最接近"精神崩溃"的物证。

### Phase 4（8/14 凌晨）：真机突破，然后被服务器封号（里程碑 24–27）

真机侧改用"安全捕获"策略：只在明文入口一个 Interceptor，VM 内部全 Stalker。

- **里程碑 24**：抓旋转。5 个 `rol/ror dword [rax],cl` 站点，30 秒内 3 次调用共 **61,023 条旋转**，逐条验证 `61,023/61,023` 符合 ROL/ROR 公式，`mismatch=0, dropped=0`。游戏存活，`Responding=True`。然后结论是："**五个旋转点是通用 VM 位旋转原语，不能再把全部命中直接等价为'密码轮'**"。61,023 条旋转全部抓完验证完，然后自己否定了自己。这是学术精神的巅峰，也是工程效率的谷底。
- **里程碑 25**：旋转正式排除。两次调用最后 768 条旋转 `768/768` 完全相同，但 keystream/nonce/plaintext 全部不同——**旋转与密码无关，实锤**。AES-GCM/ChaCha20-Poly1305/AES-256-CTR 各种 AAD 组合：零命中。
- **里程碑 26**：突破。定位到明文异或边界 `0x1809c5561 xor byte [r8], r12b`，7 次调用 6,784 字节全部验证 `after == before XOR source`，mismatch=0。顺带发现第二段分配不是 key，是 **AAD label `v3|hpac.v3.session.report.req`**。
- **里程碑 27**：完全闭合。同步捕获 `writer_sync_clean_20260814_014351` 首次在同一调用内拿到 key/nonce/plaintext/ciphertext/tag，对齐后 **`keystream == plaintext XOR ciphertext` 逐字节全部相同**。数据链闭合：VM word generator → EDX → `popfq; ret` trampoline → `store_le32` → 64 字节缓冲 → XOR。

**然而，胜利的代价是什么？**

> "该同步捕获使用全线程 Stalker，单次调用延长至约 4–6 秒，随后游戏会话进入服务端**'黑屋'**。高度疑似协议/心跳时序超时，而非内部 Interceptor 自检。已停止所有实时探针，后续优先离线分析。"

当事人成功了。同步捕获成功的那一刻，反作弊服务器把账号送进了**黑屋**。3 天的攻击，最终被服务器一个超时检测反杀。更戏剧性的是：`call 4 未完成，不可使用`——最后一条记录在捕获中途死亡；而捕获目录上还挂着一行警告："**目录含 session key 和 plaintext，不得上传**"。

当前剩余任务：恢复 `(key, nonce, block_index) → 16 words` 的 VM 生成链 + tag/MAC finalize + 7/7 独立验证。**战争仍在继续，密钥仍未到手。**

## 四、名场面合集（按惨烈程度排序）

### 1. 5.36 GB 转储，3 字节战果
为拿到请求体，转储了整个进程（10,765 个文件，5.36 GB）。读到发送缓冲区时发现：2656 个零字节，3 个非零字节，0 个可打印字符。**5.36 GB 换 3 字节，单位换算下来比黄金还贵。**

### 2. 进黑屋的那一次同步，恰好是唯一成功的一次
里程碑 27 的同步捕获是整场战争第一个"全要素闭环"的瞬间——也是最后一个。此后玩家被服务端关进小黑屋，所有实时探针永久停用。**胜利与失败发生在同一条 4–6 秒的 Stalker 记录里。**

### 3. 追了一天"栈 desync"，根因是自己模拟器漏了一行 PEB 初始化
`[gs:0x58]`。一个字节的缺省，制造了 base 槽零写、0x158 崩溃、100 次补丁、1,296,634 条指令的史诗。当事人最后写道："修复一处等价于 100 次打地鼠 patch。" ——**地鼠是自家模拟器养的。**

### 4. 61,023 次旋转，全部验证通过，然后宣布它们无关
抓全、验证、存档，最后说"这些只是 VM 通用原语"。61,023 条记录、61,023 次人工审计、0 次错配——**和密码一点关系都没有。**

### 5. 9 个版本的 TSC 反制脚本，输出 0 字节
`trace_trap_tsc.py` 到 `trace_trap_tsc9.py`，针对 RDTSC 时间检测的九个迭代，最终输出文件 `tsc_out.txt` 0 字节、`tsc2_out.txt` 0 字节。

### 6. "游戏在两次重型尾窗捕获后仍存活并 Responding=True。随后目标进程自行退出"
对象进程比脚本先崩溃/退出，文档还要严谨地注明："下一次输入访问探针附加失败是 `process not found`，不是脚本或 Frida 崩溃。" **不是你不行，是进程没了。**

### 7. AI 打 AI，人类仲裁
subagent 静态分析称"ord22 偏离 0x04"，人类交叉验证后发现是 **subagent 自己算错了**（用错常量得到 `0x7c2c16c7`，真实值是 `0x7c2c16c3`）。Rounds 10→11→12 全是 AI 的错，人类的模拟器从头到尾是对的。**这轮人机博弈，机器输了。**

### 8. 六个 deploy 脚本 + 114514
`deploy_fix.py` 到 `deploy6.py`，每个约 1,955 字节，每个都硬编码 SSH 密码 `114514`。服务器 192.168.1.30 的密码在六个脚本里出现至少六次——**这个文件夹本身就是一份泄露的密码本。**

### 9. `fake_jvm.dll`（8.7 KB）
为了骗过 `jvm.dll!JNI_GetCreatedJavaVMs` 导入，造了一个假 JVM 模块。8.7 KB 的小 DLL 站在一堆 90 MB JSON 中间，显得格外勇敢。

### 10. 里程碑文档带 SHA-256 完整性哈希
每篇文档末尾有"完整性"章节，列出脚本和 JSON 的 SHA-256。**给一场暴力逆向写学术级的可复现性声明，是知识分子最后的体面。**

## 六、悬案与未解之谜

## 七、最终鉴定

- **惨状等级**：★★★★★（满级惨，且带一个"进黑屋"的隐藏成就）
- **战损比**：投入 200+ 脚本 / 6.7 GB 磁盘 / 3 天人生 / 1 个账号；产出 27 个里程碑 / 24 篇文档 / 4 份交接 / 2 份 AI Prompt / **0 个密钥**。
- **技术遗产**（这些是实打实的）：流密码结构确认（ciphertext==plaintext 长度、16B tag、无 padding）、keystream 数据链闭合（VM word generator → EDX → store_le32 → XOR）、AES-GCM/ChaCha/CTR 全面排除、`key ^= key + 0x4111` 的 rolling key 规则、dispatch 公式、1612 handler 表、11 克隆 dispatcher、明文异或边界 `0x1809c5561`。
- **教训**：① 先初始化好 TEB 再模拟；② 别在 .bugland 里 Interceptor；③ 别在游戏心跳期间全线程 Stalker（4–6 秒足以进黑屋）；④ 别把 61,023 条旋转全抓了才发现是通用的。
