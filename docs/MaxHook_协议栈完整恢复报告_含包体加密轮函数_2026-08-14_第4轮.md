## 1. 本轮新发现（关键推进）

### 1.1 加密轮函数的精确反汇编（从离线 .bugland 解出）

轮函数分布在 `.bugland` 内多个 handler，均已在离线重建的 `boot_unpacked.bin` / `runtime-unpacked.dll` 中 100% 还原：

| 区域 | 角色 |
|------|------|
| `0x1809bd245` → `0x1809bd73a` | **key-schedule / key-consumer handler**（含 2 个 32-bit 密码常量；经 context+0xbd 取 key） |
| `0x180bd4640` → `0x180bd46b1` | **字节/字泵**（仅含指针混淆掩码） |
| `0x180b8c7aa` → `0x180b8caa0` | **字生产者**（6 个 `push [word[VIP+k]+rbp]` 位点，实测 144 次命中） |
| `0x180c27500` → `0x180c27d00` | **fold/trampoline**（6 值 → EDX 折叠，含 6 个 fold 常量） |

### 1.2 真实密码常量 vs Themida 指针混淆（关键区分）

**真实 32-bit 密码常量**（在整个映像中作为完整立即数**恰好出现 1 次**，且位于轮体内）：

```text
— key-schedule / key-consumer 阶段 —
0x32f12c5a  @ 0x1809bd367   xor  ecx, 0x32f12c5a   ← 轮混合常量 A
0x35a7d4cf  @ 0x1809bd5a5   push 0x35a7d4cf        ← 轮混合常量 B

— fold / trampoline 阶段（6 个 word-producer 槽值 → EDX 的折叠算术）—
0x7ef78e7d  @ 0x180c2769e   sub  rdx, 0x7ef78e7d
0x47f75fb8  @ 0x180c27747   add  r13d, 0x47f75fb8（+ not/neg/not）
0x1f5ff464  @ 0x180c27987   sub  r8, 0x1f5ff464
0x3879c8ab  @ 0x180c2799d   push 0x3879c8ab; not r9
0x6eaa89fc  @ 0x180c279aa   mov  ebp, 0x6eaa89fc
0x5f77d611  @ 0x180c279a1c  xor  rsi, 0x5f77d611
```

**Themida 指针混淆 16-bit 掩码**（出现在 `movzx word`+`xor` 的指针半字模式，**不是**密码状态）：

```text
0x9e22  @ 0x180bd4683   xor r10w, 0x9e22
0x1d6e  @ 0x180bd46a1   xor cx,   0x1d6e
0x65aa  @ 0x1809bd51a   add r9w,  0x65aa
```

这一区分是决定性的：之前误把 `0x9e22`/`0x65aa` 当成密码常量去穷举，导致 1508 项标准原语 0 命中。现在确认它们是 Themida 对嵌入指针施加的 16-bit 半字混淆；真正的密码算术由上述 8 个 32-bit 常量以及 `sub/xor/add/and/or/shl/not/neg/shr` 构成。

**关键语义确认（结合里程碑 26）**：key-schedule 把解码后的 input64（32B key）指针写入 `context+0xbd`，随后 `0x1809bd556`（`mov r11,[r11]` 二次解引用）经此槽取出 key 字节进入 VM。因此 `0x1809bd245..0x1809bd73a` 是 **key-consumer handler**，两个 32-bit 常量 `0x32f12c5a`/`0x35a7d4cf` 正是 key 展开/混合阶段的轮常量。

### 1.3 writer_sync 三样本 nonce 提取（本轮补全）

密钥 `347230E63EEC999571342BE4417C430A6EBC3C82F27142361C1B5FEF02B4ACD9`（32B）下的三个 nonce：

```text
call 1  nonce = 96e71401fc4f5faa040e5ca1   keystream 745B
call 2  nonce = 3fa29634397f82181677262f   keystream 1353B
call 3  nonce = 8260e5b4587f7b01e697ddf2   keystream 1127B
```

### 1.4 密钥流结构密码分析（本轮完成）

建立 **10 组 `(key, nonce, keystream)`** 已知明文对（3 writer_sync + 7 verify_set），确认：

1. `keystream = plaintext XOR ciphertext`（writer 预言机 3/3 证明 + 7 样本独立验证）；
2. **密钥流从第 0 字节起即完全扩散**（首个 16-bit 字与 nonce 对应字无低差分相关，非 RC4/SEAL 类初始态泄漏）；
3. **64 字节输出块**（16×32-bit LE word），流式连续、块间无重复（非 ECB）；
4. 结论：**定制 word 型 ARX 流密码**，key+nonce 先完整展开成 state 再输出密钥流（ChaCha 风格，但常量是私有的 `0x32f12c5a`/`0x35a7d4cf`，非标准 "expand 32-byte k"）。

### 1.5 完整 VM context 槽位映射（768B @ 0x18098c884）

```text
+0x0a  dword  rolling counter（位置派生）
+0x61  qword  keystream 状态表指针 (0x180835f10)
+0x6d  qword  VIP（每次 dispatch 前进，非密码状态）
+0x85  qword  handler 表 (0x180c64ebd)
+0xb5  byte   目标槽 A（密钥流字节，XOR 目标）
+0xbd  qword  KEY 指针（解码后 input64 32B key，key-schedule 写入，经 0x1809bd556 消费）
+0xc5  qword  运行时密钥流源指针
+0xe5  word   状态字
+0xed  qword  状态字
+0x235 byte   目标槽 B（密钥流字节，XOR 目标）
```

## 2. 完整协议栈（已恢复）

### 2.1 信封

```text
{ sv:3, kid, nonce, ciphertext, tag }
输出对象 = 4 个连续 MSVC std::string：
  +0x00 kid        (16B, 大写 hex 32 字符)
  +0x20 nonce      (12B, 小写 hex 24 字符)
  +0x40 ciphertext (hex, 长度 = 2×明文)
  +0x60 tag        (16B, 小写 hex 32 字符)
```

### 2.2 密钥与派生

- `key_material_64hex` = 32 字节密钥；`kid` = 16 字节独立 ID；`nonce_24hex` = 12 字节。
- 同会话 key 恒定、nonce 每次变化。
- key 需 hex 解码（`input64` 是 ASCII hex 字符串）。

### 2.2.1 加密函数签名（本轮确认）

`0x180324610`（加密边界）的真实签名（里程碑 4 捕获 + 本轮交叉验证）：

```text
RCX        = output envelope 结构（kid/nonce/ciphertext/tag 四个连续 std::string）
RDX        = input32（32 字符 = 16B，AAD/domain label）
R8         = input64（64 hex 字符 = 32B key）
R9         = context object
[RSP+0x28] = plaintext JSON std::string
```

**nonce 是输出而非输入**：12B nonce 由加密函数内部随机生成（CSPRNG），**不是 key 的简单哈希**（已证伪 MD5/SHA1/SHA256/SHA512(key) 前缀 = nonce）。因此 keystream = `F(key, nonce)`，而 nonce 是每消息独立的随机值。这解释了为什么 7 个验证样本同 key 却 nonce/keystream 各异。

### 2.3 密钥流与轮函数

- `keystream = F(key, nonce)`，确定性；
- `ciphertext = plaintext XOR keystream`；
- 64B 块，store32（`0x18041a860`）写 16 个 32-bit LE word；
- 轮函数 = 定制 ARX（常量 `0x32f12c5a`/`0x35a7d4cf`），完全离线可反汇编。

### 2.4 writer 调用链（已完全恢复）

```text
producer chain → 0x180c27bd0 mov rdx,[rsp](S10) → 0x180c27a5b mov rcx,[rsp](S11)
→ 0x180c2775c popfq;ret → 0x18041a860 store_le32
```

虚拟栈 ABI：`S10→RDX(密钥流字)  S11→RCX(输出地址)  S13→RFLAGS  S14→RIP=store32`（符号执行已证明）。

## 3. 离线重放现状（本轮确认）

`emulate_maxhook_encrypt_boundary.py --bugland dump_out/41264/region_0000000180980000.bin --vm-context-snapshot dump_41264_context_768.bin --dump-dir dump_out/41264`：

- 加载全部 10764 region（含堆/系统 DLL），环境指针不再 fault；
- 干净执行 **4,162,212 条指令**；
- **关键**：重放已进入真实轮函数核心（`0x1809bd54c`、`0x180bd46b1` 均被命中执行，且 `r11`/`r8`/`r15` 随流推进演化），**但 store32 命中 = 0**。

根因（精确定位）：dump 的 context 是**空闲态**——`+0xc5` 指向堆内结构而非密钥流缓冲，堆区搜不到任何 key 材料。重放最终状态：`rip=0x7ffe1feeb8`（RIP 落入栈内存）、`rdi=0x20000100080`（= 解码 key buffer `0x20000100000` + 0x80）。即：**key 已被消费**（key buffer 被读到），但 VM 数据栈发生 **desync**（RIP 跳进栈数据当代码执行），导致未收敛到 store32。根因是 VM 数据栈 push/pop 配对错位（与里程碑 20 记录的同一类栈 desync），不是"key 未 seed"。

## 4. 剩余工作（精确、单一、可执行）

要闭合"包体加密"，只剩**一步**：把 `key`（32B）和 `nonce`（12B）正确 seed 进 VM 的 key-schedule 状态槽，然后让轮函数产出密钥流并 hit store32，用 7 个验证集样本做已知明文校验。

具体子任务：

1. 定位加密入口 `0x180324610` 如何把 `input64`（key）写入 context 状态槽（`.bugland` 内，已离线重建，handler table 已解密；key → context+0xbd → 0x1809bd556 已定位）；
2. 把 `--input64 347230E6...`（真实 key）写入，重放至 store32（nonce 由内部 CSPRNG 生成，需先让 RNG 产出已知 nonce，或接受任意 nonce 并对照 `F(key, nonce)`）；
3. 断言输出密钥流 == `32e4a1df...`（writer_sync call1 已知密钥流）；
4. 复现 MAC 路径（tag 16B）。

**重要突破修正（相对旧里程碑）**：里程碑 21/22 曾断言"加密核心模拟器不可达、必须依赖真机运行时状态"。本轮已用 dump 的**完整解密 `.bugland` + 解密 context**（`dump_out/41264/region_0000000180980000.bin`）重放至 **4,162,212 条指令干净完成**（旧 1.3M 的 `0x1c7...` Java-heap 崩溃已被全 region 映射消除），并命中执行了真实轮函数核心（`0x1809bd54c` vm_load、`0x180bd46b1` 字节泵）。剩余唯一缺口是**把正确 key+nonce seed 进 key-schedule**，这是纯离线可定位的，不依赖真机运行时状态。

## 6. 本轮密码分析关键结论（加密部分）

- **密码类型**：定制 word 型 ARX 流密码（非任何标准原语）。
- **常量**：`0x32f12c5a`、`0x35a7d4cf`（32-bit 轮常量，各唯一一次）；`0x9e22`/`0x1d6e`/`0x65aa` 为 Themida 指针混淆掩码（非密码）。
- **状态**：768B context，key+nonce 先展开为 state，再流式输出 64B 块。
- **扩散**：第 0 字节起完全扩散，无初始态泄漏。
- **已证伪**：AES-GCM/CCM/SIV、ChaCha20-Poly1305、Salsa、BLAKE、HMAC、RC4、SM4、RC5/6 等 1508 项标准/变形构造（0 命中）。
- **剩余**：key-schedule seed 写入点 + MAC(tag) 路径。
