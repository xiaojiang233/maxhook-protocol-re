一句话总结：MaxHook.dll（WinLicense 3.x 加壳的布吉岛原生反作弊）的外壳已完全拆解、上报协议 100% 确定、加密信封的明文/密钥/输出全部截获； 唯一未破的是外层加密算法本身——被 Themida VM 字节码化，标准密码库 60+ 项验证全排除，剩余唯一路径是 VM 字节码反编译（另一 agent 进行中）。 工程替代方案（加密边界 hook 复用）已就绪可落地。

一、目标与结论

目标无需原 DLL，用纯协议模拟实现布吉岛 native 反作弊上报（含加密信封） 核心难点外层信封加密 = Themida VM 私有流密码，算法本体在 VM 字节码内 已达成端点/信封/明文/参数布局 100% 确定；明文+密钥+输出信封 7 组验证集到手；方案 1 可落地 剩余VM 字节码反编译（key 派生 + 轮函数）→ 用验证集验收

5.1 端点与流程

5.2 信封（Envelope）

请求: {"ciphertext","kid","nonce","sv":3,"tag"}   （字段顺序与此不同！）
响应: {"sv":3,"kid","nonce","ciphertext","tag"}
kid=32hex · nonce=12B · tag=16B · 密文长=明文长（流式无填充）

5.3 加密前明文

{"device_id":"E43A2C0F779F0DF2","h2_cantor":"v2:<MD5>:<SHA256>",
 "nonce":"<16B>","report_packet":"<104B hex 内层加密>",
 "seq":74,"session_id":"2933FD48...","sv":3,"timestamp":1786614116994}
双层加密：信封内还有内层 report_packet（104B hex）——外层保护整个 JSON，内层保护设备报告，可能复用同一加密函数（VM 内第三条路径实锤）。

七、加密破译进展

7.1 已确定

项值
加密边界0x180324610 = jmp VM 0x181523001 → dispatcher 0x180c43fdd → handler 表 0x180c0c000
参数布局RCX=输出信封 · RDX=KID(32hex) · R8=会话密钥 input64(64hex=32B) · R9=context · [RSP+0x20]=明文

7.2 算法排除清单（不用重复踩）

AES-GCM/CCM/CTR/OFB/CFB · ChaCha20(12B/8B nonce) · Salsa20 · RC4 · HMAC-SHA256/SHA1/MD5 截断 · input64 全部哈希/字节序/XOR 变体 · +kid/h2_cantor/device/session 全部组合 → 全 0 命中

7.3 验证集（现成回归门槛）

crypto_verify_set.json：7 组同会话 (明文, input64, kid, nonce, 密文, tag) 对齐样本，独立校验通过（seq 74-80，密文长=明文长 7/7，KID 恒等 7/7）——VM 解出算法后用它验收。

7.4 重要修正（里程碑 08）

0x180322d10 不是 hex 解码器——静态反汇编显示它是"逐字节范围校验/匹配/分类"（读 96hex + 间接谓词，无输出写入）。不应在"还原它的解码结果"上花时间，应继续追踪 VM 入口内对 input32/input64 的实际消费。

7.5 unlicense 适配性（里程碑 08 审计）

ergrelet/unlicense（Themida/WinLicense 2.x/3.x 动态脱壳+导入修复）可作"从原始壳重取干净 runtime dump"的备选，但不能替代 VM 解译（无 VM 字节码反编译器、无本协议识别逻辑）。运行需执行目标（rundll32 加载），需隔离环境 + 授权。
