三、认证与黑屋判定链路

1. 客户端收集事件 (class_loaded / alloc_anomaly / network_attestation) → 组装 JSON
2. 设备指纹: device_id + h2_cantor + nonce → report_packet 加密打包
3. POST security.mcbjd.net/api/v3/report (Keep-Alive 长连接, 12 分钟级)
4. 服务端校验 → 响应 {"code":200,"message":"pass","regular_id":"..."}
5. message != "pass" 或检测超时 → 服务器判定「协议无效」→ 黑屋 (periodic 判定)
6. regular_id = 布吉岛正式玩家认证 ID (SyncToken 关联)

五、对代理项目 (S1mple) 的启示

已确认: 包内容没问题, 黑屋根因 = 跨服后 minecraft:register 重注册缺失 → 服务器收不到 SyncToken 心跳与完整性上报 → periodic 判定协议无效。

协议事实: security.mcbjd.net 上报是客户端主动行为 (经代理可见域名), 代理不影响其到达性;
修复方向不变: 跨服配置阶段代答时补发 register (含 heypixel:s2cevent/sync_skins/floodgate:*), 或让客户端真实参与重协商。
