# MaxHook 协议栈证据审计与确切进度

日期：2026-08-14
性质：对既有 80+ 报告和当前代码的纠错审计。以端到端验证为最终标准。

## 一、结论先行

当前**没有完整复现协议栈**。独立实现对 24 组向量的结果是：

- `key + nonce -> keystream`：**0/24**；
- `tag`：**0/24**；
- 因此完整 `{sv:3,kid,nonce,ciphertext,tag}` 生成：**0/24**。

之前称 `maxhook_protocol_reference.py` 为“完整参考实现”、称综合检查“11 项全通过”、称“只差
8704B 栈、补上必然闭合”，均过度表述。现已修正：未实现部分统一抛出 `NotImplementedError`，
验证器改为“证据审计”，不再将结构检查冒充算法复现。

## 二、已严格证明的内容

1. **边界与布局**：入口 `0x180324610` 参数、key=32B hex decode、nonce=12B、tag=16B、kid=16B；
2. **流式异或关系**：真实样本 `ciphertext = plaintext XOR byte_stream`；
3. **writer 同步证据**：3/3 完整调用中 `0x18041a860` 的 64B writer block 等于 `pt XOR ct`；
4. **VM 证据**：4096 transition trace，handler 表/若干 handler 语义、writer trampoline ABI；
5. **非标准候选排除**：已测试 AES/ChaCha 等候选不匹配已知向量；
6. **SHA-256 初始化存在**：`0x18042b970` 写入标准 8 个 SHA-256 IV；
7. **采集缺失事实**：10 个 `vm_enter_stack` 事件均只有地址/size，无文件/字节附件。

## 三、尚未证明或已被纠正的内容

### 3.1 “tag 是 SHA-256 MAC”未证明

当前只证明某条离线重放路径初始化了 SHA-256 context。没有证明：

- 该 context 最终参与 envelope tag；
- tag 的消息输入、密钥、截断规则；
- 任何 SHA/HMAC 候选能匹配 tag（现有候选均 0/10）。

故准确表述是：**执行路径中存在 SHA-256 初始化；其用途未归因**。

### 3.2 “只差 8704B VM 栈”未证明

采集脚本确实调用 `safeBytes(low, 0x2200)` 发送栈附件；实际事件却无 `file`、`captured_bytes`、
`sha256`，说明该次 `safeBytes()` 返回 null 或附件未到达。仅凭地址元数据不能证明栈内容就是唯一缺口。

此外既有里程碑同时指出：

- `context+0xc5` / `+0x61` / 更广状态表缺失；
- 堆中 key/瞬态 key-schedule 状态缺失；
- synthetic stack 与真实 VM push/pop discipline 不一致；
- 所有离线 replay 的 `store32_trace` 仍为空。

因此准确表述是：**至少缺 VM 栈/瞬态状态；是否只缺这一个尚未验证**。

### 3.3 “fold 闭式完整”未证明

观察到多个算术块和 writer trampoline `S10 -> RDX`，但 6 槽到 S10 的完整映射尚未恢复。
不能用猜测 XOR 汇合输出。参考实现现已 fail-closed。

## 四、确切进度（按可交付功能，而非报告数量）

| 模块 | 进度 | 说明 |
|------|-----:|------|
| 信封/边界/字段编码 | 90% | 输出序列化细节仍需端到端实现验证 |
| key hex decode | 100% | 32/32 字节闭合 |
| ciphertext XOR 关系 | 100% | pt/ct/writer 多源证明 |
| VM 控制流/handler 映射 | 70% | 有 trace/核心语义，未完成全量可执行语义提升 |
| key+nonce -> keystream | **0% 可用实现** | 结构证据多，但不能生成一个正确字节 |
| tag 生成 | **0% 可用实现** | SHA-256 用途未归因，候选 0/10 |
| 完整协议栈独立实现 | **0/24** | 当前不可声称完成 |

若用“逆向理解程度”衡量，约 **65–75%**；若按用户要求的“可独立复现并通过向量”衡量，
核心加密能力仍是 **0%（0/24）**。

## 五、下一步的确定方案

### 方案 A：修复入口栈采集（先做）

不是新增 hook 点，而是修复现有安全入口采集：

1. `safeBytes(low,0x2200)` 失败时记录 `vm_enter_stack_error`，包含 Memory.query / range；
2. 按已映射 range 分段读取，避免一次跨 guard/unmapped page 导致整个 0x2200 返回 null；
3. 宿主保存每个 chunk，记录 base/offset/sha256；
4. 离线重放恢复 chunk，并启用 `--watch-stack` 验证首个 push/pop 分歧是否消失；
5. 必须以 `store32_trace` 非空且与 writer_sync 真值匹配作为成功标准。

### 方案 B：纯离线语义提升（并行/后备）

1. 用已知 dispatch trace 固定 control-flow，避免 angr `jmp symbolic` 爆炸；
2. 自定义解释器追踪寄存器派生、间接 load/store、push/pop、flags；
3. 先在手工解码的 chain A/C 上做差分单测；
4. 扩展至 54 handler；
5. 端到端以 24 组向量验证，禁止只做结构自洽检查。

## 六、完成标准

只有同时满足以下条件才能标记完成：

1. `generate_keystream(key,nonce,n)` 对 24 组向量全部匹配 `pt XOR ct`；
2. `mac_tag(...)` 对 24 组 tag 全部匹配；
3. 完整 envelope 生成 24/24；
4. 不读取捕获 ciphertext/tag 作为 oracle 输出；
5. 参考实现不再包含 `NotImplementedError`。
