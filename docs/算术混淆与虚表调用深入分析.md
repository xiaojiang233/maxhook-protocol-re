# 算术混淆与虚表调用深入分析

日期：2026-08-14。纯离线。基于 MaxHook.runtime-unpacked.dll（基址 0x180000000）反汇编 + Unicorn 具体执行。

## 一、核心机制：表驱动 ARX 混淆（helper 表 + 加密索引表）

发送调度 `0x180332770` 与 key-schedule `0x180322a20` **共用同一套混淆机制**：

```
call qword ptr [helper_table + idx*8]   ; idx 由混淆算术计算
```

### 1. helper 表 0x1807bdc70（磁盘明文，16 个通用函数）
```
[0]=0x180376ac0 ARX   [1]=0x18001c570 nop  [2]=0x1803d4050 movabs+xor+ror
[3]=0x1800493c0 getter [4]=0x180043540 setter [5]=0x1803dfa60 xor+bswap+rol
[6]=0x18005ef60 bool   [7]=0x180367b20 counter [8]=0x18031a530 XMM大函数
[9]=0x18037d240 getter [10]=0x18026ed30 check [11]=0x18039be30 xor+rol+neg
[12]=0x180383850 bytewriter [13]=0x180036550 nullcheck [14]=0x1803c6580 r9输入
[15]=0x180392e90 ARX
```
**修正此前"4 handler"误判**：这些是通用 ARX/utility 原语（getter/setter/bytewriter/bool/null-check），不是业务分支处理器。

### 2. 混淆算术模式
每个 `call [helper+idx*8]` 前是一段确定性位运算：
```
movsxd rax, [glob_index]        ; 初始索引（如 0x1807c7b78）
mov ecx, 0x394a5e26
xor ecx, [r14 + rax*4]          ; r14 = 混淆表1 (0x180658f90)
bswap ecx
mov eax, [r13 + rcx*4]          ; r13 = 混淆表2 (0x1807c3ad0)
add ecx, 0xacec895a
ror eax, cl ; inc eax ; ror eax, cl ; xor 0x5a89ecac ; bswap
call [0x1807bdc70 + rax*8]
```

### 3. 决定性发现：混淆表在磁盘上是加密的（运行时改写）
- helper 表 `0x1807bdc70` 磁盘**明文**（16 函数指针）
- 混淆表 `0x1807c3ad0` / `0x180658f90` 磁盘上是**随机加密值**（如 `0x8decac01`），**非小整数**
- **Unicorn 具体执行 + 磁盘表值**：所有 `call [helper+idx*8]` 的 idx 均远超 16（0x44b/0x184/0x6cd...）→ **证明磁盘混淆表与运行时值不一致，运行时被解密/重写**
- 静态无法恢复运行时解密值（解密逻辑/密钥不在 dump）→ **helper 具体索引的静态天花板**

### 4. 明文小整数表（可能为解密源，但无 oracle 验证）
- `0x1807c7450`：`0x1,0x1,0x2,0x2,0x8,0x6,0x1,0x1`（文档确认的"全局索引表"）
- `0x1807c7b78` 区域：`0x11,0x6,0x11,0x14,0x11,0x4,0x1c,0x11,0x13,0x15...`（send dispatcher 的初始索引源）

## 二、keystream generator（0x18041a8a0）的混淆已解（对照）

文档（keystream_generator_架构.md）确认同一 helper 机制的解法：
- 函数指针表 `0x1807d7c70`（明文，16 项，含 store32）
- 索引表 `0x1807d7cf0`（加密 4 dword）
- **deobfuscation 本质**：`fn_index = enc + 1`（rol/ror 序列净抵消为恒等或字节交换）
- 恢复 = 有限搜索（fn 表 16 项，正确值 = fn_index - 1 经反变换）
- 已确认 subcall 3 = store32 (entry 5)，subcall 0/1/2 = {2,6,9} 排列

**send dispatcher 与 generator 的区别**：
- generator 直接读 `index_table[offset]`（单级），可对 writer_sync oracle 有限搜索恢复
- send dispatcher 经**两级表索引**（r14→r13）且依赖全局索引 `0x1807c7b78`，**无 oracle 验证**其 helper 索引 → 无法用同法恢复

## 三、触发条件：静态能证明 vs 不能证明

### 能静态证明（控制流骨架 + 数据流）
1. **上报调用链**（真机栈捕获）：加密入口 `0x180324610` ← report builder `0x1803cd330` (callsite 0x1803cf7e1) → 发送调度 `0x180332770` (0x1803d0acf) → `0x18033326e` → WinHttpSendRequest
2. **report builder 含两个遍历运行时对象数组的循环**（对象数量 N/M 由运行时状态决定）→ 上报内容是对象集合的动态函数
3. **发送调度是字节码解释器/状态机**：通过 16 个通用 helper 执行操作，混淆表运行时解密

### 不能静态证明（被加密混淆表挡住）
- 每个 `call [helper+idx*8]` 实际调用的 helper（混淆表运行时值缺失）
- 顶层虚表回调的触发事件源（`call [rax]` 目标运行时确定）
- 具体"上报 vs 不报"的布尔条件语句（隐藏在混淆算术里）

## 四、结论
算术混淆的**结构**完全可静态分析：helper 表明文、混淆模式确定、加密表可识别。但**具体 helper 索引的运行时值依赖 .data 混淆表的运行时解密**，该解密在离线 dump 之外。这与 keystream generator（有 oracle 可恢复）不同，是静态分析的**可证明边界**。触发上报的具体条件分支语句因此无法从纯静态解析，但"上报内容是运行时对象集合的动态函数"已被 report builder 的循环结构直接证明。
