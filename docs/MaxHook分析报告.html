MaxHook.dll 逆向分析报告

网易中国版 Minecraft「布吉岛」服务器 heypixel 反作弊体系 — 合法客户端经 MCProtocolLib 代理被判「协议无效」根因研究
分析日期：2026-08-12 · 目标：E:\MCLDownload\Game\.minecraft\native\MaxHook.dll (24,928,616 B, PDB anti-cheat.pdb)

核心结论（TL;DR）

1. MaxHook.dll 是 WinLicense（Themida 商业壳）加壳的 JVMTI/JNI 原生反作弊，随 heypixel mod 打包分发（jar 内 lib/MaxHook.x64.dll），与「布吉岛」服务器是同一厂商的配套产品（开发路径 NativeAntiCheat\x64\Release\anti-cheat.dll）。

2. 检测面分两层：① Java mod（ZKM 混淆，1128 类）通过自定义通道 heypixel:s2cevent 上报 mod 文件哈希 + 硬件指纹（jasypt 加密），并有心跳 SyncToken；② DLL 通过 JNI 钩子（jni_call_hook::flush_and_report）挂钩 net/minecraft* 类、自带 socket 层与内嵌证书库（Certum/Sectigo）经 WinHTTP 独立直连上报，并做字节码级类文件校验（Invalid inc maxStack/size）。

3. 「协议无效」判定的直接触发点不在包内容，而在服务器切换（GAME→CONFIGURATION 重协商）后的通道重注册与完整性/心跳链路断裂：代理以 legacyServerSwitch 模式代答配置阶段，客户端停留在 GAME 态，不会向新服务器上下文重发 minecraft:register 通道注册，且 heypixel:s2cevent 的完整性上报/心跳时序被打断——服务端周期性校验缺失即周期判「协议无效」。代理源码注释已自认此风险（"Dropping them makes the server judge the client's protocol invalid (missing integrity report / sync token) after the switch"）。

4. 服务端身份校验：DLL 的 net/minecraft 类匹配器 + 自带 TLS 证书库说明它校验的是"自己的上报通道"（WinHTTP 直连）与 JVM 内的 Minecraft 类，而非 Minecraft 连接对端 IP；但经代理时 DLL 经 JNI 观察到的连接上下文是代理地址，若随上报带上环境信息，服务端可比对出异常。

一、MaxHook.dll 技术身份与加壳结构

1.1 壳识别

  • 入口 RVA 0x1F00058 位于 .boot 节（15.9 MB，熵 7.95 ≈ 纯随机加密载荷）；.bugland（22.5 MB BSS，RSize=0）与 .boot 共享同一 RawOff（0x896600）。
  • 入口为 LZ77/Deflate 风格自解压 stub（位流读取 adc dl,dl + rep movsb 回指复制）。
  • 解压流程（Unicorn 模拟完整还原）：入口 base+0x1F00058 → 调用 helper 0x1F001DF（取 EIP、算 delta、检查重定位标志）→ 循环调用解压例程 base+0x1F0005D（src=base+0x1F00248，dst=base+0x980000=.bugland）→ 完成后 jmp base+0xC0EB27（解压后真实入口，OEP 为 push rbp; jmp ... 跳板链）。
  • 壳运行期读取 gs:[0x30]（PEB）、gs:[0x188]（TLS）→ 需要完整 PEB/TEB；我们为其搭建了最小 Windows 模拟环境（真实 kernel32/ntdll 导出表 + PEB/TEB/LDR + API 分发 + JNI/JVM 伪造表），VM 运行 1 亿指令后解密出 SOFTWARE\WinLicense、Software\WLkt 等壳自身授权键。
  • 载荷解压区（boot_unpacked.bin，22.5 MB）前 2.9 MB 为低熵明文代码区（真实 OEP 代码），其余为 VM 字节码/加密数据。

1.2 来源与分发（网易绑定第一层）

  • mod jar 4689645918625526379@2@8.jar（81 MB）内含 lib/MaxHook.x64.dll（尺寸与安装版完全一致 24,928,616 B）+ lib/MinHook.x64.dll（API 钩子库，修正了此前「Detours」推断）。
  • Java 侧加载（ClientNetworkBootstrap.initializeNativeLibrary()）：extractAndLoadNativeLibrary() 从 jar 资源解压到 .minecraft/native/MaxHook.dll 后 System.load()；开发回退路径 D:\WorkSpace\IDEA\Java\HeyPixelMod\NativeAntiCheat\x64\Release\anti-cheat.dll（即项目名 NativeAntiCheat，PDB anti-cheat.pdb）。
  • 结论：MaxHook.dll 不是网易官方反作弊，而是「布吉岛」服务器（heypixel 生态）自带的客户端反作弊组件——与服务器同一厂商，随 mod 分发。

二、DLL 检测与通信能力（静态证据链）

2.1 JNI 类名匹配器（核心：钩 Minecraft 类）

RVA 0x18D790 处反汇编还原为：

bool is_net_minecraft(const char* s) {           // rcx = JNI 类名字符串
    if (strlen(s) < 13) return false;
    return memcmp(s, "net/minecraft", 13) == 0;  // movabs 立即数构造, 避免明文串
}
; movabs rax, 0x656e696d2f74656e   ; "net/mine"
; movabs rdx, 0x7466617263656e69   ; "inecraft"
; xor rax,[rcx]; xor rdx,[rcx+5]; or rdx,rax; sete al; ret

用途：DLL 经 jni_call_hook 过滤 net/minecraft* 类的 JNI 调用（FindClass/GetStaticMethodID 等），用于观察/挂钩 Minecraft 客户端网络类。C++ RTTI 明文（.data）：jni_call_hook::flush_and_report（static，含 std::vector<std::basic_string<char>> 记录队列）——收集 JNI 调用记录并批量上报。

2.2 类文件校验 / 字节码插桩能力

明文错误串 Invalid inc maxStack/size —— 来自 Java class 文件解析/验证器。结合「匹配 net/minecraft 类」与 JVMTI agent 角色，DLL 具备在类加载时校验甚至改写 Minecraft 类字节码的能力（JVMTI ClassFileLoadHook 类能力）。

三、Java mod 侧全貌（完全逆向）

3.1 通道与协议

  • mod 为 ZKM 24.0.2 混淆（1128 个类，含 emoji 命名混淆类）；com.heypixel.client 客户端包 112 文件已完全逆向。
  • Forge 通道：heypixel:s2cevent（包 233=String 服务器 UI 事件 / 250=MuxFragmentMessage 完整性上报 / 234=图片）、floodgate:form、floodgate:netease。
  • MuxFragmentCodec：协议版本 1，按 sequence 分片重组（FragmentAccumulator，单包上限 16 MB，分片 60s 过期）。
  • 线格式（本地抓包样本 + 代理日志确认）：0xFA + int32 BE variant + zlib(JSON)（S2C 配置推送）、0x01/0x02 + opaque（C2S 完整性上报）、0x0C + empty（控制/心跳）、heypixel:sync_skins（0x01+0x24+UUID hex，皮肤同步）。

3.2 完整性上报（RemoteAssetMessage）

  • 进服即发 SPRINT 型上报；服务器经 PlayerMetadataMessage 下发动作（SPRINT/SNEAK/SWIM/ATTACK/NULL/ASD），客户端对应回复。
  • 内容：加载的 mod 文件列表 + 路径 + SHA-256、user.dir、java.home、CPU（ProcessorID）、主板（厂商/型号/序列号/HardwareUUID）、全部网卡（名称/MAC/IPv4/IPv6）、磁盘序列号、integrity token（主/次）——经 jasypt 加密（密码 = 随机 clientId UUID），MessagePack 编码后分片发送。

3.3 心跳与管道

  • NetworkHeartbeatMessage（包 ID 12）：进服一次性发送 SyncToken（服务器下发的令牌，客户端回显），登出清除。
  • PacketPipelineInjector：登录时在 Netty pipeline 的 packet_handler 前注入 PacketInterceptHandler（ChannelDuplexHandler），对每个入站/出站包广播事件（可取消/替换）。混淆层另有包拦截类（引用 Packet/ServerboundCustomPayloadPacket/ClientPacketListener/Connection）。

五、代理链路分析（S1mple / MCProtocolLib 1.20.6）

5.1 代理行为

  • 完成网易 X19 认证（自定义 AES/RSA + sauth），双 leg 独立压缩/AES 状态。
  • 状态桥接：LOGIN/CONFIG 扩展包按白名单转发；GAME 态全量转发（含全部 custom payload）。
  • legacyServerSwitch（关键路径）：后端服务器做 GAME→CONFIGURATION 重协商时，若客户端处于 GAME（网易 1.20 客户端不支持动态重协商），代理代答整个配置阶段（SelectKnownPacks 回显服务端列表、KeepAlive 自答、FinishConfiguration 代发），客户端保持 GAME；期间将客户端 GAME 态 custom payload（heypixel:s2cevent 等）转发给后端。

5.2 证据：代理作者已确认的断链点

// ProxyConnection.java L187-196

    // While the backend is being switched (backend=CONFIGURATION, client still GAME),
    // the client keeps sending business-channel payloads (heypixel:s2cevent integrity
    // reports/heartbeats, floodgate:* etc). Dropping them makes the server judge the
    // client's protocol invalid (missing integrity report / sync token) after the switch.

即：代理作者已观测到「丢包 → 协议无效」的直接因果（missing integrity report / sync token），并为此加了转发。但转发不解决 minecraft:register 通道注册的重注册问题（见结论）。

六、根因结论与证据链

6.1 「协议无效」触发链（按证据强度排序）

#触发项证据强度
A 服务器切换后完整性/心跳链路未在新上下文重建：布吉岛/网易服务器群切换（GAME→CONFIG 重协商）后，客户端（GAME 态）不会向新上下文重发 minecraft:register，代理代答的配置阶段也不包含 heypixel 通道注册；服务端新上下文收不到 RemoteAssetMessage 完整性上报与 SyncToken 心跳 → 周期校验失败 → 周期判「协议无效」 代理源码注释（5.2）；服务端判定具周期性（四章）；s2cevent 协议完全依赖通道注册（三章）；heypixel.log 周期节奏与服务端判定周期吻合 高
B MaxHook.dll 观察到的连接上下文与期望不符：DLL 经 JNI 钩 net/minecraft 网络类；经代理时对端是局域网代理地址而非网易服务器；DLL 自带 socket 层/WinHTTP 独立通道的上报数据中若包含连接对端/环境指纹，服务端比对异常 2.1 类匹配器；2.3 独立通道；RemoteAssetMessage 上报网卡/环境（3.2）；代理为局域网地址 中（需运行态确认）
C 分片重组丢失：MuxFragmentCodec 分片包在代理转发/延迟下若乱序或超 60s 过期，FragmentAccumulator 丢片 → 完整性上报不完整 3.1 分片机制；日志 C2S 上报量大但无法确证丢片 中
D DLL 自身周期性检测上报（#5/#6 慢检）未达服务端：DLL 的 WinHTTP 独立通道不经过代理，若其上报要求与 Minecraft 连接同会话绑定（如校验 SNI/证书链后回传会话签名），代理会话下不成立 2.3 独立 TLS；四章慢检节奏 低-中（推断）

6.2 回答关键疑点

  • Wireshark/抓包检测？ 检测名单（进程名/工具名）位于 WinLicense 加密载荷内，未在解压区明文出现；DLL 确具备进程枚举能力路径（FNV 解析器 + 环境采集），但静态上未获名单项。运行态 Procmon/npcap（内核级，避开 VEH 反调试）可确认。另注意：DLL 自带 socket 层 + WinHTTP，其网络特征检测重点更可能是「自己通道的 TLS 指纹」而非 Wireshark 进程。
  • 服务器身份校验？ 有「校验」但对象是自己上报通道的 TLS 对端（内嵌 Certum/Sectigo 证书库）；对 Minecraft 连接对端 IP 的校验未获直接证据（mod 逆向源码不读 ServerData/remoteAddress）。「走代理必然触发」的更稳机制是 A（通道重注册缺失）与 B（连接上下文异常）。
  • 与网易绑定在哪层？ ①随 mod jar 分发（System.load）；②mod 通道与服务器联动（s2cevent/floodgate）；③DLL 独立 WinHTTP 通道 + 证书库（可能上报到服务器配套端点）；④launcher 目录/文件版本校验（GetFileVersionInfoA/GetTempPath2W 导入）。
  • 上报通道？ Java 侧完全已知（heypixel:s2cevent 包 250，jasypt+MessagePack）；DLL 侧 WinHTTP URL 加密（需运行态抓包，见第七节）。

七、验证方案（运行态取证清单）

7.1 客户端（Windows）

  1. Procmon（内核驱动，VEH 反调试不可见）：过滤 MaxHook.dll → 记录文件访问（.minecraft/native、launcher、temp）、注册表（SOFTWARE\WinLicense、Software\WLkt、启动器键）、进程创建/读取。
  2. npcap 内核级抓包（绕开用户态 Wireshark 触发面）：定位 WinHTTP 目标 IP/端口 + TLS SNI（证书校验失败时 SNI/证书名直接可见）。重点看 #5/#6 慢检（~1000ms 周期）是否对应新 TCP/TLS 连接。
  3. 对比干净/代理两种环境 heypixel.log 的 #1–#10 节奏与 #9/#10、#5/#6 的耗时异常（若代理环境下某档耗时跳变/缺失，即该档为触发项）。
  4. 断开状态监控：代理切换前后抓 s2cevent 双向流量，确认 minecraft:register（config 态）与 250 号分片包是否在切换后仍被服务端接受。

7.2 代理（Arch 主机）

  1. 在 legacyServerSwitch 路径补打日志：确认切换后服务端是否再收到客户端 ServerboundCustomPayloadPacket(minecraft:register)；若没有 → 手动在配置阶段代答阶段补发 minecraft:register（含 heypixel:s2cevent/heypixel:sync_skins/floodgate:*）再观察「协议无效」是否消失。
  2. 用 3h 日志的 payload dump（/opt/s1mple/payload-dumps）回放 C2S 上报，检查分片序号是否有空洞（MuxFragment 丢片）。
  3. 试验：切换后若持续黑屋，改为「不代答配置、让客户端参与重协商」（若网易客户端实际支持），或切换后强制客户端重新登录。
