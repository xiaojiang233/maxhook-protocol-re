# MaxHook key-schedule 状态定位 — 最终综合（第 116 轮）

日期：2026-08-14
范围：纯离线。

## 一、解决第 96 轮与第 112 轮的表观矛盾

| 轮次 | 结论 | 前提 |
|------|------|------|
| 96 | "0 个真正 key 派生字节" | 假设 3 调用 = 3 个不同 key |
| 112 | "47 字节跨调用不同" | 实测跨调用变化的字节 |
| 113-114 | 3 调用 = **同 key + 3 nonce** | 同线程/同 retval/JSON 明文 |

**综合结论**：
1. 3 调用**同 key**，故"跨调用不变的字节"（663 字节）= **key 派生状态 + 模块常量/指针的混合**，
   无法区分（只有单一 key，无法分离 key 派生 vs 固定常量）；
2. "跨调用变化的字节"（47 字节）= **nonce/计数器派生**（第 115 轮已分类为计数器 vs 真密码状态）；
3. 第 96 轮"0 key 派生字节"是**正确的**（方法正确，但前提"3 不同 key"错误导致无法识别 key 派生）；
4. 第 112 轮"47 字节"是 **nonce 派生**（非 key 派生），两者不矛盾。

## 二、决定性结论

key-schedule 的 **key 派生状态在 context 的 663 个跨 nonce 不变字节中**，但因本地只有
keystream_history 一个会话含活态 context（且该会话 key 未知、只有单一 key），无法将 key
派生状态与模块常量/指针分离。这解释了：
- 为什么 round 96 正确测得 "0 key 派生字节"（单一 key 下 key 派生 = 常量，不可区分）；
- 为什么需要"第二个同会话不同 key"或"key 字节 + 同会话活态 context"才能分离。

## 三、精确的缺口（最终、无可再收窄）

要复现 key_schedule_expand()，需要以下任一（本地均无）：

1. **同会话 + key 字节**：keystream_history（pid 42948）有活态 context 但无 key 字节；
   有 key 的会话（verify-set/writer_sync/boundary2/keytrace）均无活态 VM context；
2. **同会话 + 第二个 key**：分离 key 派生 vs 固定常量（需同一进程用两个不同 key 加密并
   同时 dump context，本地无）。

这是**纯数据缺口**：所有代码结构（ARX 轮函数、控制流、常量、槽位）100% 离线可读，
key-schedule 输出的**结构**（663 固定 + 47 nonce 派生 + 计数器）已精确测定，
仅缺"key 派生状态的分离"所需的一个额外数据点（同会话第二 key 或 key 字节）。
