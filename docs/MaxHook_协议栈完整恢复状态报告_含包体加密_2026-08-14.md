# MaxHook 协议栈完整恢复状态报告（含包体加密）

日期：2026-08-14（第 N 轮）
范围：纯离线。资源：原版 `MaxHook.dll`、`dump_out/41264`（10764 个内存 region）、`crypto_verify_set.json`（7 个完整样本）、各捕获。

## 0. 结论

协议栈已**分层闭合**至"包体加密轮函数"这一最后一层。已完整恢复：

1. 信封结构 `{sv,kid,nonce,ciphertext,tag}`；
2. key/kid/nonce/tag 的字节布局（32B key / 16B kid / 12B nonce / 16B tag）；
3. `.boot` → `.bugland` 离线解压（99.96%）；
4. Themida 重定位/fixup（`.bugland` 100% 匹配运行态）；
5. writer（store32）调用语义与虚拟栈 ABI；
6. 密钥流 = plaintext XOR ciphertext 的完整对应关系；
7. 已解密 handler table 与完整初始化的 VM context（来自 dump）。

**剩余未闭合**：`(key, nonce) → keystream` 的轮函数 + `→ tag` 的 MAC。这是定制 ARX 流密码（非任何标准原语，已穷举 AES-GCM/CCM/SIV、ChaCha20-Poly1305、Salsa、BLAKE、HMAC 等 1508 项，0 命中）。

## 1. 本次新发现（关键推进）

### 1.1 dump 含完整初始化的 `.bugland` 与 context

`dump_out/41264/region_0000000180980000.bin`（22528000 字节）是**运行时 `.bugland`**，与 `runtime_bugland2.bin` 99.998% 一致，且：

- **handler table `0x180c64ebd` 已解密**（项为有效地址 `0x18098ade4` 等）；
- **fixup slot `0x18098f97c` 已修复**（`0x1809a62b3`）。

dump 内 `.bugland` 的 context（`0x18098c884`，768 字节）是**完整初始化的运行时状态**：

```text
+0x0a rolling key = 0xffffffa5
+0x45 = 0x180836d10
+0x61 = 0x180835f10   (keystream 状态表指针)
+0x6d VIP        = 0x181d2879b
+0x85 handler表   = 0x180c64ebd
+0xb5 = 0x1808374e0
+0xc5 = 0x5966fffbe0  (指向堆区 0x5966ff6000 内的状态结构)
```

### 1.2 关键：dump 是"空闲态"，不是"加密中瞬时态"

- `0x5966fffbe0` 指向的结构内容为表指针集合（`0x180835f10`、`0x1808374e0` 等），**不是**密钥流缓冲区。
- dump 堆区（6 个大 region）中**搜索不到**任何已知 key 材料（verify-set `30bfeafe...` 或 writer-sync `347230e6...`）。
- 结论：dump 时刻进程**不在加密**，key 已清除，context 是"上次加密结束的残留态"，密钥流缓冲区（加密时动态生成）不在 dump。

### 1.3 因此"包体加密轮函数"必须离线执行 VM 才能复现

密钥流 = `F(key, nonce)` 是确定性函数，代码在 `.bugland` VM。复现路径：

1. 用 dump 的完整初始化 `.bugland`（handler table 已解密）；
2. 用 dump 的完整 context（作为 key-schedule 的持久状态起点）；
3. 从加密入口 `0x180324610` 喂入 key（input64）和 nonce；
4. 让 VM 执行 key-schedule + 轮函数，hit store32。

之前的 offline replay 已推进到 4.16M 指令干净退出，但未 hit store32，根因是 **key-schedule 初始化阶段的环境依赖**（native 堆指针 `0x1ab783620d0`、系统 DLL 指针 `0x7ffcb75a6fe4`）被 zero-fill。

## 2. 完整协议栈（已恢复部分）

### 2.1 信封

```text
{ sv:3, kid, nonce, ciphertext, tag }
输出对象 = 4 个连续 MSVC std::string：
  +0x00 kid        (16B, 大写 hex 32 字符)
  +0x20 nonce      (12B, 小写 hex 24 字符)
  +0x40 ciphertext (hex, 长度 = 2×明文)
  +0x60 tag        (16B, 小写 hex 32 字符)
```

### 2.2 密钥与派生

- `key_material_64hex` = 64 hex 字符 = **32 字节**密钥；
- `kid` = 16 字节（不是 key 的 MD5/SHA1/SHA256 前 16 字节，是独立的 ID）；
- `nonce_24hex` = 12 字节；
- 同一会话 key 恒定、nonce 每次变化（7 样本验证）；
- key SHA-256 指纹 = `a340fb925d80`（验证集）。

### 2.3 密钥流

- `keystream[i] = plaintext[i] XOR ciphertext[i]`；
- 64 字节块，每块由 store32 写 16 个 32-bit LE word；
- store32 = `0x18041a860`，EDX = 最终 32-bit 密钥流字（writer_sync 3/3 证明）；
- 密钥流是流式连续的，块间无重复（非 ECB）。

### 2.4 writer 调用链（已完全恢复）

```text
producer chain (0x180afc853 -> 0x180bc0334 -> 0x18099089e -> 0x180bce798 -> 0x180b8c7aa)
-> 0x180c27936/276c5/279e4/2769b/27945/27b86/2754f/27582   (RDX 变换 + 压栈)
-> 0x180c278a7 -> 27786 -> 27652 -> 27bf9 -> 279b4 -> 27673
-> 0x180c27bd0 mov rdx,[rsp]   (S10)
-> 0x180c27a5b mov rcx,[rsp]   (S11)
-> 0x180c27900 -> 0x180c2775c popfq;ret
-> 0x18041a860 store_le32
```

虚拟栈 ABI（`symbolic_writer_trampoline.py` 证明）：

```text
S10 -> RDX (密钥流字)   S11 -> RCX (输出地址)   S13 -> RFLAGS   S14 -> RIP=store32
```

## 3. 完整恢复的离线重放现状

`scripts/same_instance_pipeline.py --apply-fixup`：

- `.boot` 解压 → 就地 fixup → 真实入口 `0x180c0eb27`；
- `.bugland` 与运行态 100% 匹配；
- 直接调用 `0x180324610`，跑 24,011 条指令（修复后）；
- 追加每消费者表修复后（`0x180a831db`→0x180835f10、`0x180bf1eb2`→0x1808374e0），干净退出 4,162,212 条指令；
- **但 store32 命中 = 0**（未进入密钥流循环）。

## 4. 剩余工作（精确、可执行）

要闭合包体加密，需恢复 **key-schedule 初始化协议**，即：

1. 加密入口如何把 input64（32B key）和 nonce（12B）喂入 VM context 的状态槽；
2. key-schedule 的确定性展开（从 key+nonce 到 context 各状态槽 + 密钥流缓冲区）；
3. 轮函数（producer chain 的真实 ARX 算术）；
4. MAC（tag 16B 的生成）。

这些都在 `.bugland` VM 代码内（已 100% 离线重建、handler table 已解密），但被 Themida 混淆（大量 `mov 0; or 0x400; and 0x80` 噪声）。剩余工作 = 对 producer chain 做符号去混淆 + 用 7 个验证集样本做已知明文验证。
