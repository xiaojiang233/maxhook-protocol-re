# MaxHook native 协议里程碑 19：崩溃点语义解析与 0x158 构建链闭合

时间：2026-08-13（Asia/Shanghai）
范围：完全离线的 Unicorn 重放（session 2 / call 4），带全寄存器指令窗口（`--trace-window-start`），不附加进程。

## 结论

把 `encrypt_vm_watched_650k` 中 545691 处的崩溃从"黑盒崩溃"升级为**带完整数据流证据的确定性崩溃链**：

1. 崩溃指令 `0x1809bd556`（`mov r11, [r11]`，r11=0x158）是一次 **vm_load 原语的第二次解引用**；
2. `0x158` 不是 epoch 垃圾，而是精确计算出来的：`0x2b << 3`，其中 `0x2b` 来自 `[0x1808a4a40]`（.data 节一个 dword）；
3. 崩溃根因是 **context 槽 `+0x26`（base 槽）在崩溃前被 handler `0x1809c0078` 写成 0**：该 handler 用 `pop r8` 从真实执行栈 `[rsp]=[0x7ffe1fec50]` 弹出 0；
4. 对比同一 handler 序列的成功执行（inst 514336 组），`+0x26` 槽在成功组是 `0x1807b6980`（有效 base），最终目标 `0x564 + 0x1807b6980 = 0x1807b6ee4` 指向可读内存；
5. 因此该执行路径的语义是 **base + index*8 的表查找**（slot 先写入 index，左移 3 得字节偏移，再加 base 槽），崩溃 = base 槽被零写，并非加密原语本身出错。

## 一、崩溃点：vm_load 原语

崩溃 handler 主体 `0x1809bd4xx–0x1809bd556`：

```asm
0x1809bd502  movzx r11, r11w          ; 取低 16 位偏移
0x1809bd52a  add   r11, rbp           ; r11 = context + offset
0x1809bd54c  mov   r11, [r11]         ; 第一次解引用：r11 = [context+0x45] = 0x158
0x1809bd556  mov   r11, [r11]         ; 第二次解引用：r11 = [0x158] -> CRASH
```

崩溃时（inst=545689/545691）寄存器：

```text
r11 = 0x18098c8c9 = context + 0x45 (slot)
qword [0x18098c8c9] = 0x158
```

即：`context+0x45`（slot）里存的不是指针，而是 0x158。

## 二、slot=0x158 的完整构建链（全部来自指令窗口）

| inst | rip | 指令 | 效果 |
|---|---|---|---|
| 544693 | 0x180bd46b7 | `mov [rcx], r10` | rcx=context+0x45（slot），r10=[context+0xbd]=0x2b → slot=0x2b |
| 544964 | 0x180a728e5 | `shl [rax], cl` | rax=slot，cl=3（rcx=0x87d5f503）→ **0x2b<<3 = 0x158** |
| 545297 | 0x180bceca2 | `add [r8], r9` | r8=slot，r9=[context+0x26]=0 → 0x158+0=0x158（不变） |

两次栈/上下文读的关键验证（trace window 原始寄存器）：

```text
544693 前: rcx=0x18098c8c9, r10 的来源 = [0x18098c941] = [context+0xbd]
533727 前: 0x180a353e9 mov [r14], edx 写入 context+0xbd，edx=[0x1808a4a40]=0x2b
545297 前: r9 的来源 = [0x18098c8aa] = [context+0x26]
```

## 三、根因：context+0x26 被零写

`context+0x26`（0x18098c8aa）的完整写入历史（`encrypt_vm_ctxwrites.json`，全 context 写跟踪）：

```text
514072  rip=0x180ade406  value=0x1807b6980   ; 成功组：有效 base
534128  rip=0x1809ee8b9  value=0x1807b6980
538814  rip=0x180a92294  value=0x2b
542239  rip=0x1809908ec  value=0x2b
543464  rip=0x1809c0078  value=0x0           ; 崩溃组：base 被清零
```

`0x1809c0078` 的 handler 片段（真实字节）：

```asm
0x1809c005e  pop r8                          ; r8 = [rsp]; rsp += 8
...
0x1809c0078  mov [rdx], r8                   ; rdx = context+0x26
```

`pop r8` 从 `[0x7ffe1fec50]` 弹出 **0**（该栈位置在线程入口/调用边界后未写过非零值）。

## 四、成功组对照：同一序列、有效 base

inst 514336 组（成功）：

```text
514336  0x180ade406  mov [rdx], r14   ; slot = 0x159
514561  0x180a728e5  shl [rax], cl    ; cl=2 -> 0x159<<2 = 0x564
514887  0x180bceca2  add [r8], r9     ; r9=[context+0x26]=0x1807b6980
        -> slot = 0x564 + 0x1807b6980 = 0x1807b6ee4  (可读)
```

同一个 `0x180bceca2` handler（`add [r8], r9`）在两组执行中：
- 成功组 r9=0x1807b6980 → 目标可读；
- 崩溃组 r9=0（因为 +0x26 槽被 `0x1809c0078` 清零）→ 目标 0x158 不可读。

## 五、语义归纳：base + index*8 表查找

两组合并后 handler 序列一致：

```text
slot = [context+0xbd]        ; index 初值（0x2b / 0x159）
slot <<= cl                  ; ×8 → 字节偏移
slot += [context+0x26]       ; + base（0x1807b6980 / 0）
ptr  = [slot]                ; 最终解引用
```

这是 Themida/WinLicense VM 中常见的 **数据/跳转表基址+索引** 访问模式。崩溃只是 base 槽被零写导致越界读，**不说明外层加密算法有问题**。

## 六、为何模拟里 base 槽是 0

`0x1809c0078` 依赖 `pop r8` 从真实执行栈取回一个之前压入的值；离线模拟从 entry 恢复栈时，`0x7ffe1fec50` 附近未由 boundary capture 恢复（capture 只恢复 builder frame / 字符串对象 / context），因此栈槽为 0。这是**离线栈状态缺口**，不是 VM 字节码自身错误。修复方向：从 `encrypt_boundary_capture2` 恢复调用栈更深区域，或在重放前把该栈槽 patch 成成功组的值继续前推。

## 七、工具与复现

模拟器新增：

- `--trace-window-start N`：从第 N 条指令起记录每条指令的 bytes + 全寄存器 + VIP；
- `vm_pointer_slot_writes[]`：现在记录**整个 context 0x200 字节内的全部写**（含 old_bytes），不再只盯 slot。

复现命令：

```powershell
python target\emulate_maxhook_encrypt_boundary.py `
  --boundary-dir target\encrypt_boundary_capture2 `
  --boundary-session 2 --boundary-call 4 `
  --max-instructions 650000 --timeout-ms 30000 `
  --trace-window-start 544000 `
  --output target\encrypt_vm_tracewin_544k.json
```

结论输出（同次运行，`--output` 可换）：

```text
instruction_count = 545691
error = 'Invalid memory read (UC_ERR_READ_UNMAPPED)' @ 0x1809bd556 addr=0x158
```
