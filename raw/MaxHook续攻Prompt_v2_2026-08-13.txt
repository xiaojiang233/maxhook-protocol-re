## 二、已确认的协议事实（不要重新验证）

1. 上报端点 `security.mcbjd.net/api/v3/report`，POST JSON，三层流程：bootstrap/redeem → session/exchange → 周期 report
2. 信封 `{sv:3, kid, nonce(12B), ciphertext, tag(16B)}`，密文与明文等长 + 16B tag
3. 明文 JSON 字段：`{"device_id","h2_cantor":"v2:<MD5>:<SHA-256>","nonce","report_packet":"<104B hex 内层>","seq","session_id","sv":3,"timestamp"}`（**双层加密**：外层信封 + 内层 report_packet）
4. **外层加密是 VM 字节码化的私有流密码**：AES-GCM/CCM/CTR/OFB/CFB/ChaCha20/Salsa/RC4 及 key 派生组合 7 样本全 0 命中；.bugland 无任何标准密码常量
5. **input64（64-char hex，会话级）第一步就是直接 hex 解码成 32-byte 原始会话材料**，无额外 KDF/哈希（里程碑 18 已证明，heap 输出逐字节 == bytes.fromhex(input64)）
6. 参数布局（hook 验证 7/7）：RCX=output envelope（4 个 std::string: kid+0x00/nonce+0x20/ciphertext+0x40/tag+0x60）、RDX=KID hex、R8=64-char key material、R9=context、[RSP+0x20]=plaintext JSON

## 四、崩溃点 0x158 构建链（里程碑 19，已完全闭合）

离线模拟（session2/call4，max 650k）在 **inst=545691** 崩于 `0x1809bd556 mov r11,[r11]`，r11=0x158。完整数据流：

```
533727  0x180a353e9 mov [context+0xbd], edx     ; edx=[0x1808a4a40](.data dword)=0x2b
544693  0x180bd46b7 mov [slot], r10             ; r10=[context+0xbd]=0x2b -> slot=0x2b
544964  0x180a728e5 shl [slot], cl              ; cl=3 -> 0x2b<<3 = 0x158
545297  0x180bceca2 add [slot], r9              ; r9=[context+0x26]=0（被零写）-> 0x158
545689  0x1809bd54c vm_load: [context+0x45]=0x158 -> [0x158] CRASH
```

**根因**: `context+0x26`（base 槽）在 **inst=543464** 被 `0x1809c0078`（`mov [rdx],r8`，r8 来自 `pop r8`=[0x7ffe1fec50]=0）清零。成功对照组（inst 514336 组）同一序列 base=0x1807b6980，最终 `0x564+0x1807b6980=0x1807b6ee4` 可读。

**语义归纳**: 该 handler 序列 = `base + index*8` 的表查找。崩溃 = 离线模拟栈 [0x7ffe1fec50] 未恢复（boundary capture 只恢复了 builder frame/字符串对象/context），**不是 VM 字节码错误**。

## 七、下一步建议（按性价比排序）

1. **修复模拟器栈缺口继续前推（最短路径）**：崩溃唯一原因是 base 槽被零写。两个做法任选：
   - 改 `emulate_maxhook_encrypt_boundary.py` 的 boundary 恢复，把 `0x7ffe1fec50` 附近调用栈内容从 capture 恢复；
   - 或做 patch 实验：在 `0x1809c0078` 执行前把 `[rsp]` patch 成 `0x1807b6980`（成功组 base），验证能否越过 545691，看能否推进到 PLAINTEXT/OUTPUT 首次解引用。
2. **追踪 32-byte 解码 key buffer 的第一位 consumer**（里程碑 18 遗留）：监控 allocation `0x20000100000`（离线）的读取，记录读取者 RIP/VIP/rolling key，传播标签到密码状态。目前 400K 指令内该缓冲仍无读取。
3. **继续静态 handler 语义归一化**：崩溃 handler 组（0x180bd46b7 / 0x180a728e5 / 0x180bceca2 / 0x1809bd54c / 0x1809c0078 / 0x180a353e9）已确认是槽拷贝/左移/加法/vm_load 原语，可作为语义基准继续标注其它 handler。
4. **另一条线（已可用）**：方案 1 Envelope 服务（proxy 集成真实 MaxHook 加密输出）已 7/7 验证可落地，与 VM 硬破并行，谁先出结果都能推进。

## 八、避免重复踩坑（重要）

- **Frida Stalker transform 回调统计的是"翻译次数"不是"运行时执行次数"**——所有依赖 count 的结论已降级，不要再用
- `runtime_bugland2.bin` 是异步末态，**不能当作同步函数入口状态**；正确做法是 boundary capture 同步快照
- hook 明文混淆函数会触发 Themida 反篡改崩溃（改 .text 字节），用 Stalker 动态插桩或离线 Unicorn
- `struct.pack('<I', 负数)` 溢出会被误判为 unicorn 崩溃，用 `<i`
- input64 在 capture 里被二次 hex 编码（readStr hex 解码后是 ASCII 字符串）
- 里程碑 09-15 的"执行次数=1"论证已降级为"首翻译顺序"，仅作 CFG 交叉校验，不作运行时目标证据
- **确定性崩溃 ≠ epoch 垃圾**：0x158 = 0x2b<<3 是精确计算值，先追数据流再怀疑状态
